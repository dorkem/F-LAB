## 데이터를 가져오는 순서
- MySQL엔진으로부터 시작
### 1. 파서
- 사용자가 요청한 SQL문을 쪼개 트리로 만든다.
- 문법검사를 수행한다.

```sql
SELECT name, price FROM menu WHERE price > 10000;
```
- Root: `SELECT`
  - Child1: `name`, `price`
  - Child2: `menu`
  - Child3: `>`
    - Left: `price`
    - Right: `10000`

<br>

### 2. 전처리기
- 파서에서 만든 트리를 바탕으로 SQL 문장에 `오타와 구조적인 문제`를 찾음
- `DB 접근권한` 확인
- from 절에 테이블 및 뷰가 실제로 있는 오브젝트인지 확인

<br>

### 3. 옵티마이저
- 파서에서 검사가 끝난 쿼리를 가지고 사용자가 요청한 데이터를 빠르고 효율적으로 찾아갈 수 있도록 `실행 계획`을 세운다.

<br>

### 4. 익스큐터
- MySQL엔진과 스토리지 엔진에 걸터있는 오브젝트
- 옵티마이저에서 만든 실행계획을 바탕으로 스토리지 엔진에서 `데이터를 가져온다.`

<br>

### 5. 스토리지 엔진
- 실행계획을 바탕으로 실제로 데이터를 가져오는 물리적인 작업을 수행한다.
- OTLP 환경으로 `ACID`, `Row Lock`, `MVCC`(읽기는 쓰기를 기다리지 않음)등을 지원하는 `InnoDB`엔진을 보통 이용한다.
- ```sql
  select engine, transactions, comment from information_Schema.engines;

<br>

### 6. 결과전달
- 최종적으로 MySQL엔진에서 데이터를 조인하거나 필터링해서 데이터를 사용자에게 전달한다.

## 조인알고리즘 용어
- 이게 다 실행계획을 고치는 알고리즘임
### 드라이빙과 드리븐
```sql
SELECT * FROM shops s    -- FROM뒤 드라이빙 테이블
JOIN orders o            -- JOIN뒤 드리븐 테이블
  ON s.shop_id = o.shop_id
WHERE s.category = '치킨' -- 조건 1: 치킨집은 전국에 10개뿐
  AND o.status = 'COMP'; -- 조건 2: 완료된 주문은 100만 건
```
- 드라이빙: 조인의 기준이 되어서 먼저 읽힘
- 드리븐: 뒤늦게 접근하여 드라이빙의 결과를 기반으로 읽음
- 드라이빙에서 결과를 작게 가져와야 드리븐에서 시간을 덜먹음(옵티마이저가 해주긴함)

### 중첩 루프 조인(Nested Loop JOIN)
1. 드라이빙 테이블에서 category = '치킨'인 데이터를 찾음(10개라고 가정)
2. 10번 반복하는데, 한 번에 status = 'COMP'인걸 `order`테이블(드리븐)에서 계속 스캔함
- 인덱스가 없으면 매번 디스크에 방문하는 `랜덤엑세스`가 발생될 수 있다.

<br>

### 블록 중첩 루프 조인 (Block Nested Loop Join)
- 드라이븐을 돌면서 드리븐에 접근하니 너무 비효율적이므로, 조인 버퍼에 드라이빙 테이블에서 찾은 `레코드`를 담아두고, 드리븐을 돌면서 버퍼내 드라이븐의 요청에 대한 결과를 대조하는 방식

<br>

### 배치 키 액세스 조인 (Batched Key Access Join)
- 드리븐 테이블의 데이터가 디스크에 여기저기 흩어져 있으면, 인덱스가 있어도 디스크 헤더가 왔다 갔다 하느라 성능이 떨어진다.
- 드라이빙의 조건 1개당 루프를 도는게 비효율적이므로, 조인버퍼에 드라이빙 테이블에서 찾은 `조인키`를 담아두고, 이 키가 디스크에 흩어져있으니 순서에맞게 실행계획을 고친다

<br>

### 해시조인 (Hash Join)
- 인덱스가 없을 때, 메모리에 잠깐 해시맵을 만들어서(빌드), 드라이븐을 읽으며 바로 일치하는 값을 반환(프로브)한다.
