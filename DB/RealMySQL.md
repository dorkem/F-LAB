# 🦅RealMySQL
## 📍 4.2.3 MVCC(Multi Version Concurrency Control
### 쓰는 이유
- 이전에는 락이 걸려있으면 쓰는 중에 읽는게 불가능해 지연이 많이 발생했다. 따라서 `MVCC`는 `Undo 로그`를 이용해 쓰기 중에도 읽기를 허용함으로써, 락(Lock) 없이 데이터의 과거 버전을 조회하게 만드는 기술이다.

### Undo Log
- 변경(UPDATE / INSERT / DELETE)이 일어나면 변경 전의 내용을 Undo 로그, 변경 이후에 내용을 Redo 로그에 기록한다.
  - 장애 발생시 커밋 된 내용은 Redo 다시 쓰고, 미커밋된 내용을 Undo를 보고 다시 쓴다.
- 실행 취소시: 데이터 변경시 이전 값을 언두로그에 기록하기 때문에, 쿼리 실행 중 에러가 발생하거나, `Rollback`시 사용된다.
- MVCC에서 과거 버전 보여줄 때: 트랜잭션이 데이터를 수정중일 때, 다른 사용자가 데이터를 조회하면 수정전의 데이터를 보여줌
- 장애 복구시: 시스템이 `COMMIT`이전에 종료되면 다시 시작될 때, Redo를 통해 마지막 상태를 만들고, 커밋되지 않은 언두 로그를 참조하여 모두 롤백시킨다.


### 잠금 없는 일관된 읽기(Non-Locking Consistent Read)
- InnoDB 스토리지 엔진은 MVCC 기술을 이용해 잠금을 걸지 않고 읽기 작업을 수행한다.
- 특정 사용자가 레코드를 변경하고 아직 커밋을 수행하지 않았다고 하더라도, 이 변경 트랜잭션이 다른 사용자의 SELECT 작업을 방해하지 않는 것을 잠금 없는 일관된 읽기라고 표현한다.
  - 격리 수준에 따라서 다른데 `READ_UNCOMMITTED`인 경우 변경된 값을 바로 보고, `READ_COMMITTED`, `REPEATABLE_READ`인 경우에는 UNDO로그를 통해 본다.
- 빨리 트랜잭션을 종료해야 Undo로그가 쌓인다는 단점을 줄일 수 있다.

## 📍 5.1 트랜잭션
### 스토리지 개요
- `InnoDB` 스토리지 엔진: 트랜잭션 제공 O
- `MyISAM`, `MEMORY` 스토리지 엔진: 트랜잭션 제공 X → 정합성이 떨어짐

### 락
- `MySQL 엔진락`: 스토리지 엔진 락에 영향을 줌
  - 글로벌 락
    - 서버에 존재하는 모든 테이블을 닫고 잠금을 건다.(비용도 높고 작업도 멈춰야 함)
    - DB에 존재하는 MyISAM, MEMORY 스토리지 엔진의 테이블에 대해 mysqldump로 일관된 백업을 받아야할 때 글로벌 락을 사용(InnoDB에서는 백업 락이라는게 도입되었다. 백업 시 레플리카 서버에서 글로벌 락을 획득해서 진행함)
  - 테이블 락
    - 테이블에 거는 락으로 명시적, 묵시적인 락을 검
    - 묵시적 락은 쿼리가 실행되는 동안 자동으로 획득됐다가 쿼리가 완료한 후 자동해제(InnoDB에서는 **레코드 기반 잠금**이기 때문에 묵시적인 테이블락이 걸리지 않음, DDL에만 영향을 줌)
  - 네임드 락
    - 사용자가 지정한 문자열에 대해 획득하고 반납(해제)하는 잠금
    - 배치 프로그램 처럼 한번에 많은 레코드를 변경해야하는 쿼리에 네임드락 사용하면 간단히 해결 가능
  - 메타데이터 락
    - 테이블 데이터에 거는게 아닌 테이블 정의 자체(컬럼정보, 인덱스정보, 제약조건, 테이블 속성)에 거는 락
    - Online은 메타데이터 락(MDL) 때문에 서비스가 멈추는 문제를 줄이려고 나온 기술
      - ```
        📝 사전 지식
        • UPDATE / INSERT는 레코드 락 (MDL Read Lock)
        • ALTER TABLE은 MDL Write Lock
        •	MDL은 “정의(설계도)”를 보호하는 락
        
        🍀 온라인 DDL
         ALTER TABLE 요청
        → MySQL 엔진: MDL Write 요청
        → (기존 UPDATE/INSERT 끝날 때까지 대기)
        → MDL Write 획득 (아주 잠깐)
        → 테이블 정의 변경 준비
        → MDL Write 해제
        → (백그라운드 DDL 작업 진행)
        → 다시 MDL Write 획득 (아주 잠깐)
        → 새 테이블 정의로 스위치
        → MDL Write 해제

        🍀 그 사이에 DML동작 
         UPDATE/INSERT 요청
        → MDL Read 획득
        → (DDL 중이지만 정의는 일관됨)
        → 레코드 락 획득
        → 데이터 변경
        → COMMIT
        → MDL Read 해제
        ```
      - DDL의 ‘제어’는 단일 스레드라서, 구조 변경을 완성하려면 모든 행을 다시 써야 해서 오래걸림. 따라서 그 작업을 pk기준으로 내부적에서 병렬로 처리한다.
- `스토리지 엔진락`:
  - 레코드 락:
    - 인덱스의 레코드를 잠근다.
    - `where id = 5`라면 id가 5인 행을 잠그면 인덱스에서 잠궈야함
    - 인덱스가 없는 컬럼으로 UPDATE를 수행하면 InnoDB는 PK 인덱스를 풀스캔하며, 조건에 해당하는 모든 인덱스 레코드에 하나하나 락을 건다.
    - 세마포어: 입장 티켓 수 관리(세마포어 3 = 3자리 남음)
    - performance schema: MySQL내부에서 누가 뭘 잡고있는 지 관찰하는 블랙박스로 너무 오래 락을 갖고있으면 KILL로 제거 가능
  - 갭 락:
    - 인접한 레코드 사이의 간격만을 잠그는 것(아직 데이터가 없는 인덱스 값 구간에 새 레코드를 못 넣게 막는 것)
    - pk가 1, 3 이렇게 있다고 쳤을때 `select * from a where id between 1 and 3` 이런식으로 락걸면 다른놈이 2에다 insert같은거 할 때 접근안됨
  - 넥스트 키 락
    - 레코드 + 갭락
    - mysql복제시 마스터 서버에는 바이너리 로그를 `STATEMENT` 포멧(무슨 SQL을 실행했는지), `ROW` 포멧(어떤 행이 어떻게 바뀌었는지) 두가지를 사용하는데 레플리카 서버에서는 STATEMENT 포멧을 읽는다. (트랜잭션 시작 할 때와 같은 것을 봐야하니 `REPEATABLE_READ` 격리수준으로 봐야함)
      - 근데 이건 데드락이 발생하거나 다른 트랜잭션을 기다리게 하는 일이 자주 발생하기 때문에 바이너리 로그 포멧을 ROW로 변경해서 넥스트 키 락 / 갭락을 줄이는게 좋음
  - 자동 증가 락
    - 자동증가 값이 한 번 증가하면 줄어들지 않는 이유는 지금 상태를 보는데 비용이 많이 들기 때문이다.

## 📍 5.2 격리 수준
### 정의
- 동시에 실행되는 트랜잭션을 서로의 작업을 얼마나 안본척 할 수 있게 할지 정하는 것
- 트랜잭션A가 끝나지 않았는데 트랜잭션B가 A를 보면 빠르긴 하겠지만 안보는게 안전하다.

### 트랜젝션 격리 레벨 4가지와 발생할 수 있는 문제점
1. `READ UNCOMMITTED` (커밋되지 않은 읽기)
    - 다른 트랜잭션이 수정한 후 아직 커밋하지 않은 데이터도 읽을 수 있다.
    - `Dirty Read`가 발생할 수 있다.
    - A가 데이터를 수정하고 커밋하지 않았는데 B가 그 값을 읽음. 만약 A가 롤백하면 B는 존재하지도 않는 가짜 데이터를 들고 있게 됨.
2. `READ COMMITTED` (커밋된 읽기)
    - 커밋이 완료된 데이터만 읽을 수 있습니다. Oracle의 기본값이며, `MVCC`(Undo 로그)를 사용해 커밋 전에는 이전 값을 보여준다.
    - `Non-Repeatable Read`가 발생할 수 있다.
    - 한 트랜잭션 내에서 같은 쿼리를 두 번 실행했는데, 그 사이에 다른 트랜잭션이 값을 수정/커밋하면 두 번의 조회 결과가 다르게 나타남.
3. `REPEATABLE READ` (일관된 읽기)
    - 자신의 트랜잭션이 시작되기 전에 커밋된 내용만 읽습니다.  InnoDB의 기본값입니다.
    - InnoDB가 순차적으로 증가하는 트랜잭션 고유 번호를 비교해 자신보다 늦은 번호의 데이터는 Undo 로그를 통해 내 번호보다 이전 데이터를 조회한다.
    - `Phantom Read`가 발생할 수 있다.
    - InnoDB의 로우 락은 실존하는 행만 잠궈 '빈 공간'을 방어하지 못하며, 새로 삽입된 행은 '이전 기록(Undo)'이 존재하지 않아 필터링되지 않고 유령처럼 나타난다.
    - 그래서 갭락(빈 공간을 잠금), 넥스트 키 락(레코드+갭 락)을 사용해서 빈 공간을 다 잠궈 거의 발생하지 않는다.
4. `SERIALIZABLE` (직렬화 가능)
    - 제일 강한 격리 수준입니다. 읽기 작업에도 공유 잠금(Shared Lock)을 걸어, 다른 트랜잭션이 해당 데이터를 절대 수정하거나 삽입할 수 없게 만듭니다.
    - 느리다.

| | Dirty READ | NON - Repeatable read | phantom read |
|:---:|:---:|:---:|:---:|
|READ UNCOMMITED|O|O|O|
|READ COMMITED|X|O|O|
|REPEATABLE READ|X|X|O|
|SERIALIZABLE|X|X|X|

## 📍 8.1 디스크 읽기 방식
### 개요
- 데이터베이스의 성능 튜닝은 어떻게 디스크의 I/O로 줄이느냐가 중요함
- CPU나 메모리등 전기적 특성을 띈 장치는 발전했지만, 디스크같은 기계식 장치의 성능은 제한적으로 발전됨
  - 디스크 원판에 의존하는 HDD(병목이 심함)보다는 요즘 SSD(전자식 저장매체)+플래시 메모리가 활용하고 있음

<br><br>

## 📍 8.1.2 랜덤 I/O와 순차 I/O
- 디스크 원판을 돌려서 읽어야 할 데이터가 저장된 위치(디스크 헤더를 옮겨서 읽어야함)
  - 랜덤 I/O
    - 요청 3번에 디스크 헤더 3번
    - 보통 `인덱스 범위 스캔`에 사용
    - 디스크가 읽는 위치가 연속적이지 않아서 랜덤이라고 쓴거임
  - 순차 I/O
    - 요청 3번에 디스크 헤더 1번 (디스크 헤더를 얼마나 적게 옮기는가가 관건이므로 더 빠름)
    - 큰 테이블의 레코드를 대량으로 읽을 때 사용(`풀스캔`)

- 순차는 1->2->3->4 이렇게 순차적으로 접근하고, 랜덤은 2->1->4->3 이렇게 접근하는건데 똑같이 4번 접근하는게 아닌가?
  - 순차는 2번 3번도 달라고 할 것을 예측하고, 메모리에 올리기 때문에 디스크에 접근하지 않아도 바로 꺼내줄 수 있음

## 📍 8.3 B-Tree 인덱스
- `MyISAM`은 인덱스 리프 노드가 바로 데이터 주소를 가리키지만,
- `InnoDB`는 인덱스 리프 노드가 PK를 가리키고, 그 PK로 다시 `클러스터드 B+Tree`를 한 번 더 타서 데이터를 찾는다.
- 이때 클러스터드 B+Tree는 PK 기준으로 정렬된 구조이며 리프 노드에 실제 데이터 행이 저장되어 있다.

<br>

### 인덱스 키 삽입/삭제/수정
- `추가`할 때는 정렬된 B+Tree에서 적절한 리프 노드를 탐색해 키와 주소를 저장하며, 노드가 가득 차면 분리(split)되어 브랜치 노드까지 확장될 수 있다.
- `삭제`시에는 해당 리프 노드를 찾아 즉시 제거하지 않고 삭제 마크를 남기며 디스크 쓰기 작업이 발생한다.
- `변경`은 기존 키를 삭제한 뒤 새로운 키를 다시 추가하는 방식이어서 삽입과 삭제가 모두 수행되어 비용이 가장 크다.

<br>

### 인덱스 레인지 스캔
1. 인덱스에서 조건을 만족하는 값이 저장된 위치를 찾음(=인덱스 탐색)
2. 필요한 만큼 인덱스를 차례로 읽음(=인덱스 스캔)
3. 2번에서 읽은 인덱스 키, 레코드 주소를 통해 레코드가 저장된 페이지를 가져와서 최종 레코드를 읽음

**커버링 인덱스**
- 커버링 인덱스란, 조회에 필요한 컬럼이 모두 인덱스 리프 노드에 포함되어 있어 레코드 주소를 따라 데이터 페이지를 다시 읽는 단계가 생략되는 인덱스 조회 방식이다.
  - 원래는 조건에 대해서 하나하나 찾아서(풀스캔) 반환이 되지만 인덱스를 걸면 거기에 대한 조건을 한번에 찾아오는게 가능한데,
  - 커버링 인덱스는 쿼리에 필요한 컬럼을 2개든 3개든 걸어서 인덱스로만 처리되는 경우를 커버링 인덱스라고 함.
  - (`select age, name from people`)이면 age name을 인덱스로 걸면 바로 값 반환됨)
- 그럼 인덱스 레인지 스캔에 3번은 사용하지 않아도 되서 조회성능은 좋아지지만 인덱스가 너무 커지거나, 쓰기성능이 박살나거나, 캐시효율이 떨어질 수 있음

<br>

### 인덱스 풀스캔
- `인덱스 풀 스캔`은 인덱스 구조 전체를 읽는 것으로, 데이터 페이지를 직접 읽지 않아 I/O가 상대적으로 적고 커버링이면 테이블 접근이 없다.
- `테이블 풀 스캔`은 테이블의 모든 데이터 페이지를 읽어 조건과 무관하게 모든 레코드를 검사하므로 I/O 비용이 가장 크다.

<br>

### 루스 인덱스 스캔, 스킵 인덱스 스캔
- `루스 인덱스 스캔`은 인덱스를 전부 읽지 않고 GROUP BY나 MIN/MAX에 필요한 리프 노드만 건너뛰며 읽는 방식이다.
- `스킵 인덱스 스캔`에서 복합 인덱스란 여러 컬럼을 순서대로 묶은 인덱스(`CREATE INDEX idx_user ON user(age, gender);`)이고, 선행 컬럼 조건(age에 대한 조건)이 없으면 DB는 그 값을 가능한 경우로 나눠 가정해 같은 인덱스를 여러 번 탐색하는데, 이를 스킵 인덱스 스캔이라 한다.

## 📍 클러스터드 인덱스
- 클러스터드 인덱스는 프라이머리 키(PK)를 기준으로 값이 가까운 레코드들을 같은 데이터 페이지에 묶어 저장하고, 인덱스의 리프 노드에 실제 레코드가 들어 있는 구조임
  - InnoDB는 데이터 페이지 주소 대신 레코드 자체를 클러스터드 인덱스 리프에 저장함으로써 불필요한 추가 I/O를 줄인다. 
- 클러스터드 인덱스에서 PK 변경은 단순 업데이트가 아니라 데이터 재배치와 전체 인덱스 갱신을 동반하는 고비용 작업이다.

### PK가 없을 때
1. PK가 있으면 기본적으로 프라이머리 키 기준
2. Not Null 옵션의 유니크 인덱스 중 첫번째 인덱스를 클러스터링 키로 선택
3. 그거 마저 없으면 자동으로 유니크한 값을 가지도록 증가하는 칼럼을 내부적으로 추가함

### 클러스터드 인덱스의 장단점
- **`장점`**
  - PK로 검색할 때 처리 성능이 빠르다. (특히 범위 검색이 빠름)
  - 커버링 인덱스로 바로 처리가능
- **`단점`**
  - 클러스터링 키 값이 클수록 전체적으로 인덱스가 커짐(세컨더리, 프라이머리키)
  - 세컨더리를 통해 PK를 한 번 더 조회해야해서 성능이 느림
  - Insert시에 프라이머리 키에 의해 레코드 저장 위치가 결정되어서 느림(수정시에도 삭제 삽입이라 느림)

## 📍 오라클과 MySQL과의 구조적 차이
### 오라클(통합 스토리지)
- DB 서버들이 통합된 물리적인 스토리지를 `공유`한다.
- 저장소가 하나라서 데이터가 꼬이지 않는다.
- 데이터를 복사하는 시간이 필요 없어서, DB 서버만 키우면 서비스를 키울 수 있다.(하지만 입구는 한 개라서 병목현상이 발생할 수 있음)
- 저장소가 한개라 저장소 자체가 고장나면 전체 시스템이 죽는 `Single Point of Failure`과, 접속자가 몰리면 하나의 통로로 몰리기 때문에 네트워크 속도가 느려지는 `병목현상` 발생
- 서버간 데이터 충돌을 막는 하드웨어가 필요해서 비용이 비쌈

### MySQL의 (Master-Slave/Replication)
- `Master`: "쓰기 전용". `CUD`를 담당함
- `Slave`: "읽기 전용". Master의 데이터를 로그를 통해 복제받아 보관하며, 사용자의 `R`을 처리
- 나누는 이유
  - 보통 앱에는 읽는 사람이 더 많으므로, 마스터 서버가 CRUD를 100% 다 하지않고, 읽기작업을 여러 슬레이브로 나눠서 처리함(`쿼리오프로딩`)
  - 마스터가 불타도, 슬레이브를 마스터로 승격시켜서 서비스를 이어서 할 수 있게됩니다.
  - (`Orchestrator`가 장애감지, 슬레이브 상태 확인, 스토리지에 로그들을 슬레이브에 반영, 승격, 나머지 슬레이브가 마스터를 바라보도록 재구성하는 과정)
- 마스터 DB 접속은 `@Transactional`, 슬레이브 DB 접속은 `@Transactional(readOnly = true)`
- 데이터 변경이 잦으면 마스터에서 슬레이브로 보내는 로그 관리가 힘들고, 마스터가 죽었을때 장애 복구 시 복잡해지는 경우가 있다.
