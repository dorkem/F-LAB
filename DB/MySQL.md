# 🐬MySql 트랜잭션
## 📍 트랜잭션이란
- 여러 가지 일을 '하나의 덩어리'로 묶는 것으로, 무조건 다 같이 성공하거나 다 같이 취소되어야 합니다.

<br><br>

## 📍트랜잭션 동기화란
- 과거에는 DB 작업을 위해 Connection 객체를 모든 메서드에 파라미터로 전달해야 했는데, 코드가 너무 지저분해지므로, 커넥션 객체를 `ThreadLocal`에 넣어두고, 커넥션이 필요할 때마다 꺼내쓰도록 만든것

<br><br>

## 📍트랜잭션의 ACID 원칙
### Atomicity (원자성) - "All or Nothing"
- 트랜잭션 내의 작업은 모두 성공하거나, 아니면 아예 없던 일처럼 실패해야한다.
- A의 잔고에서 1만 원을 뺐는데, B의 계좌에 넣는 과정에서 에러가 났으면 A의 돈도 원상복구 되어야한다.

### Consistency (일관성) - "법칙 준수"
- '잔고는 0원 미만이 될 수 없다'는 제약조건이 있다면, 잔고가 부족한 사람의 송금 트랜잭션은 아예 거부되어야 한다.
- 트랜잭션이 성공적으로 끝나면, 데이터베이스는 언제나 일관된 상태(규칙이 지켜진 상태)여야 한다.

### Isolation (격리성) - "끼어들기 금지"
- 여러 트랜잭션이 동시에 실행될 때, 서로의 작업에 간섭하면 안된다. 마치 혼자 실행되는 것처럼 격리되어야 한다.
- A가 통장 잔고를 조회하고 있는 도중에, B가 그 통장의 돈을 출금해버려서 A가 엉뚱한 잔액을 보게 만들면 안된다.

### Durability (지속성) - "영구 보존"
- 트랜잭션이 성공적으로 완료(Commit)되었다면, 그 결과는 영구적으로 반영되어야 한다.

<br><br>

## 정규화를 하는 이유
### 이상현상을 해결하기 위해
- 삽입이상: 데이터를 삽입하기 위해 불필요한 정보까지 함께 입력해야 하는 상황
    - 학생이 수강 신청을 안 하면 학생 정보 자체를 등록하지 못함.
- 갱신 이상: 중복된 데이터 중 일부만 수정되서 데이터 간 불일치가 발생하는 상황
    - 사용자의 주소가 바뀌었는데, 10개의 주문 기록 중 5개만 수정됨.
- 삭제 이상: 정보를 삭제할 때 유지되어야 할 다른 정보까지 연쇄적으로 삭제되는 상황.
    - 강의 수강 기록을 지웠는데 학생의 개인정보까지 같이 날아감.

### 정규화 
1. 제1정규형: 모든 칸에는 하나의 값만 들어가야한다.
2. 제2정규형: 기본키의 일부분에만 의존하는 열이 없어야한다.(부분 함수 종속 제거)
3. 제3정규형: 기본키가 아닌 열끼리 의존하는 관계가 있어서는 안된다.(A->B, B->C라는 이행 종속을 제거해야한다.)

# 🐬 인덱스
## 📍DB 인덱스의 자료구조와 동작 원리
1. 인덱스가 없으면 테이블 풀 스캔을 때리기 때문에 데이터가 늘어날 수록 조회가 느려진다.
2. 그래서 B(Balanced)-Tree를 도입해서 항상 정렬된 상태로 유지해서 값을 찾을때 풀스캔(O(N)을 하는 대신에, O(logN)의 속도로 데이터를 찾을 수 있다.
3. 기수성(카디널리티)이 높은 값을 찾아야 한다. (기수성이 높으면 값의 종류가 많고 중복이 적음) ex) 주민등록번호, ID, email등
4. CUD는 매번 정렬을 해야해서 R을 위해 희생시키는 구조임
5. 인덱스가 너무 많으면 옵티마이저가 어떤 인덱스를 쓸지 고민하고, 실행계획을 세우느라 시간이 많이걸린다.
6. 따라서 조건절에 자주 등장하거나, 데이터 수정보다 조회가 많고, 데이터 규모가 클 때 사용해야한다.

- 조건절로 조회하면 DB는 테이블 대신 B-Tree 인덱스를 먼저 보고, 루트 노드에서 해당 위치의 리프 노드 주소를 찾아가 결과를 반환함

### 📍이진트리와 B-Tree의 차이
- `이진트리`는 자식 노드가 최대 2개, `B-Tree`는 M개
- `이진트리`는 자식 노드가 추가되면 위 아래로 길어지고(데이터가 , `B-Tree`는 양옆으로 뚱뚱해짐

## 📍클러스터드 인덱스
- 클러스터드 인덱스는 프라이머리 키(PK)를 기준으로 값이 가까운 레코드들을 같은 데이터 페이지에 묶어 저장하고, 인덱스의 리프 노드에 실제 레코드가 들어 있는 구조임
  - InnoDB는 데이터 페이지 주소 대신 레코드 자체를 클러스터드 인덱스 리프에 저장함으로써 불필요한 추가 I/O를 줄인다. 
- 클러스터드 인덱스에서 PK 변경은 단순 업데이트가 아니라 데이터 재배치와 전체 인덱스 갱신을 동반하는 고비용 작업이다.

### PK가 없을 때
1. PK가 있으면 기본적으로 프라이머리 키 기준
2. Not Null 옵션의 유니크 인덱스 중 첫번째 인덱스를 클러스터링 키로 선택
3. 그거 마저 없으면 자동으로 유니크한 값을 가지도록 증가하는 칼럼을 내부적으로 추가함

### 클러스터드 인덱스의 장단점
- **`장점`**
  - PK로 검색할 때 처리 성능이 빠르다. (특히 범위 검색이 빠름)
  - 커버링 인덱스로 바로 처리가능
- **`단점`**
  - 클러스터링 키 값이 클수록 전체적으로 인덱스가 커짐(세컨더리, 프라이머리키)
  - 세컨더리를 통해 PK를 한 번 더 조회해야해서 성능이 느림
  - Insert시에 프라이머리 키에 의해 레코드 저장 위치가 결정되어서 느림(수정시에도 삭제 삽입이라 느림)

## 📍 트랜잭션 어노테이션이 JPA, MyBatis 등에서 변경 없이 동작 가능한 이유

- 어떤 DB가 들어오든 `PlatformTransactionManager`라는 약속이 있다.
- 어떤 기술이든 트랜잭션 시작은 `getTransaction()`, 커밋은 `commit()`, 롤백은 `rollback()`
- 그러면 JPA는 엔티티매니저 쓰고, 마이바티스는 커넥션 씀
