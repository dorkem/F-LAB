# 🕸️HTTP The Definitive Guide
## 📍 HTTP란?
- Hypertext Transfer Protocol로 전 세계의 웹브라우저, 서버, 웹 애플리케이션은 이 프로토콜로 대화한다.
- 신뢰성 있는 데이터를 전송한다.
- 기본요소에는 Http server(웹서버), Http client(서버에게 요청하는 것)가 있다.

<br><br>

## 📍미디어 타입
- 인터넷은 수천가지 데이터를 다루기 때문에 HTTP는 웹에서 전송되는 객체 각각에 신중하게 MIME라는 데이터 포멧 라벨을 붙인다.
  - HTML로 작성된 텍스트 문서는 `text/html`라벨
  - plain ASCII로 작성된 텍스트 문서는 `text/plain`라벨
  - JPEG로 작성된 이미지는 `img/jpeg`라벨

<br><br>

## 📍 URI과 URN
### URI(=URL)
- Uniform Resource Identifier로 인터넷의 우편물 주소 같은 것이다.
- 특정 서버의 한 리소스에 대한 구체적인 위치를 서술한다.
  - `http://`는 URL의 제알 앞단인 Scheme(스킴)이라고 불리는데 보통 프로토콜을 서술한다.
  - `www.naver.com` 두번째 부분은 웹서버의 인터넷 주소를 서술한다.
  - `/news/header.gif` 마지막 부분은 웹 서버의 리소스를 가르킨다.
 
### URN
- Uniform Resource Name으로 콘텐츠를 이루는 한 리소스에 대해, 그 리소스의 위치에 영향을 받지않는 역할을 한다.


<br><br>

## 📍 트랜잭션
### 메서드
- `GET`: 서버에서 클라이언트로 지정된 리소스를 보내라
- `PUT`: 클라이언트에서 서버로 보낸 데이터를 저장한 이름의 리소스로 저장해라
- `DELETE`: 저장한 리소스를 서버에서 삭제해라
- `POST`: 클라이언트 데이터를 서버 게이트웨이 애플리케이션으로 보내라
- `HEAD`: 지정한 리소스에 대한 응답에서, HTTP 헤더 부분만 보내라

### 상태코드
- `200`: 문서가 바르게 반환됨
- `302`: 다른 곳에 가서 리소스를 가져와라
- `404`: 리소스를 찾을 수 없음
- 보통 이렇게 상태코드와 "OK와 같은 `사유구절`과 함께 응답한다.

### 여러 객체로 이뤄진 웹페이지
- HTML 뼈대를 한 번의 트랜잭션으로 가져온 뒤 이미지, 그래픽 조각 등을 가져오기 위해서 추가로 HTTP 트랜잭션들을 수행함.
- 웹페이지는 하나의 리소스가 아닌 `리소스의 모음`

### 메시지
- 시작줄: 요청이라면 무엇을 해야하는지, 응답이라면 무슨 일이 일어났는지 나타냄
- 헤더: 구문분석을 위해 콜론으로 구분된 하나의 이름과 하나의 값으로 구성된다.
  - 1줄에 필드 1개, 헤더는 빈줄로 끝남(CRLF)
- 본문: 요청의 본문은 웹 서버로 데이터를 실어보내고 응답의 본문은 클라이언트에게 데이터를 반환함
  - 텍스트와 임의 이진데이터 포함(이미지, 비디오등)가능

<br><br>

## 📍 TCP커넥션
- 메시지가 TCP 커넥션을 통해 메시지가 옮겨지는가?

### TCP/IP
- HTTP는 애플리케이션 계층 프로토콜로 자신의 메시지를 전달하기 위해 **TCP/IP에게 reliable한 전송**을 맡김
  `TCP`
  - 오류 없는 데이터 전송
  - 순서에 맞는 전달(데이터를 보낸 순서대로 받음)
  - 조각나지 않는 데이터 스트림
- `IP`
  - Internet protocol 주소와 포트번호를 사용해서 클라이언트와 서버간 커넥션을 맞아야한다.
  - 호스트명은 DNS에서 IP로 변환가능함 

### Telnet
- HTTP는 TCP/IP를 사용하고, 문자열 기반이라 키보드로 목적지의 TCP포트로 연결하고(귀찮은걸 대신해줌), 출력 포트를 화면으로 연결해줌

<br><br>

## 📍 프로토콜 버전
### HTTP/0.9
- 간단한 HTML만을 받아오는 용도

### HTTP/1.0
- HTTP 헤더, 추가 메서드, 멀티미디어 객체를 처리

### HTTP/1.0+
- `Keep-alive` 커넥션 지원
- 가상 호스팅 및 프락시 연결 지원

### HTTP/1.1
- 더 복잡해진 웹 애플리케이션과 배포를 지원
- 현재 HTTP 버전

### HTTP/2.0
- 구글의 SDPY프로토콜 기반으로 성능개선을 위해 만드는 중

<br><br>

## 📍 웹의 구성요소
### `프락시`
- 클라이언트와 서버사이에 위치한 중재자로 클라이언트의 모든 HTTP 요청을 받아 서버에 전달한다.
  - 보안을 위해 동작하고 요청과 응답을 필터링해서 초딩들 야동 막음

### `캐시`
- 자주 접근하는 찾는 것의 사본을 저장해두는 특별한 종류의 HTTP 프락시 서버임

### `게이트웨이`
- 다른 서버들의 중개자로 동작하는 서버로, HTTP 트래픽을 다른 프로토콜로 변환하기 위해 사용
- 본인은 자기 스스로가 리소스를 갖고 있는 실제 서버인 것 처럼 요청을 다뤄서, 클라이언트가 자신이 게이트웨이와 통신하고 있다는 사실을 알아채지 못함.

### `터널`
- 두 커넥션 사이에서 날 데이터를 열어보지 않고 그대로 전달해주는 HTTP 어플리케이션

### `에이전트`
- 사용자를 위해 HTTP요청을 만들어주는 클라이언트 프로그램
- 사람의 통제 없이 스스로 웹을 돌아다니며 HTTP 트랜잭션을 일으키고, 콘텐츠를 받아오는 자동화된 사용자 에이전트가 있음
  - 스파이더, 웹로켓 등
 

<br><br>

## 📍 개요
- `HTTP`: 인터넷의 배달원
- `HTTP 메시지`: 무언가를 담아 보내는 소포

## 📍 메시지의 흐름
- `HTTP 메시지`는 HTTP APP간 주고받은 데이터의 블록으로 `클라이언트`, `서버`, `프락시` 사이를 흐름
- 메시지의 방향은 `인바운드`, `아웃바운드`, `업스트림`, `다운스트림`이 있다.
  - 인바운드: 클라이언트 → 서버
  - 아웃바운드: 서버 → 클라이언트
  - 다운스트림: 클라이언트 -(요청)→ 서버 -(응답)→ 클라이언트
  - 업스트림: 다운스트림의 흐름 속에서 다운스트림이 걸어왔던 곳

## 📍 시작줄
### 메서드
- `GET`
  - 서버에서 리소스를 요청해서 어떤 문서를 가져온다.
- `HEAD`
  - GET처럼 동작하지만, 서버의 응답으로는 헤더만 돌려준다.
  - 리소스를 가져오지 않고 리소스의 변경여부, 개체 존재 유무, 그에 대한 타입등을 알 수 있음
- `POST`
  - 서버에 입력 데이터를 전송하기 위해 설계되었다.
  - HTML폼을 지원하기 위해 흔히 사용된다.
- `PUT`
  - 서버에 문서를 쓴다.
  - PUT /product_list.txt
- `TRACE`
  - 메시지가 프락시를 거쳐 서버에 도달하는 과정을 추적한다.
  - 클라이언트는 자신과 목적지 사이에 있는 모든 HTTP 애플리케이션의 요청/응답의 연쇄를 따라가며 자신이 보낸 메시지가 망가졌거나 수정되엇는지, 어떻게 변경되었는지 확인이 가능함
- `OPTIONS`
  - 서버가 어떤 메시지를 수행할 수 있는지 확인한다.
- `DELETE`
  - 서버에서 문서를 제거한다.
### 상태코드와 사유구절
**`100-199` 정보성 상태구절**
- `100` Continued
  - 클라이언트: 서버가 다루기 어려운 큰 엔터티를 보내지 않으려는 목적, 최적화용으로 사용해야함(남발하면 서버가 오다는건지 만다는건지 모름), 서버에서 응답을 받을 때 까진 보내지 말고 기다리면, 타임아웃 이후에 자동으로 보내짐
  - 서버: expect 헤더가 없는 요청에는 100 continued 보내지 마라(이미 클라이언트는 바디 보냈을 수도 있음 = 프로토콜 꼬임)
- `101` Switching Protocols
  - 서버가 프로토콜을 바꾸었다.

<br>

**`200-299` 성공 상태코드**
- `200` OK
  - 정상요청
- `202` Accepted
  - 요청은 받아들여졌지만 서버는 어떤 동작도 수행하지 않음
- `203` Non-Authoritative Information
  - 엔티티 헤더가 원래 서버가 아닌 사본에서 왔다.
- `204` No Content
  - 웹 브라우저를 새 문서로 이동시키지 않고 갱신하고자 할 때 사용
- `205` Reset Content
  - 브라우저에게 현재 페이지에 있는 HTML 폼에 채워진 모든 값을 비우라고 말한다.
- `206` Partial Content
  - 부분/범위 요청이 성공함
  - 응답은 `Content-Range`와 `Date` 헤더를 반드시 포함해야하고, `Etag`와 `Content-Location`중 하나의 헤더도 반드시 포함해야함

<br>

**`300-399` 리다이렉션 상태 코드**
- `300` Multiple Choices
  - 요청한 URL이 가리킬 수 있는 리소스가 여러 개라서, 서버가 후보 목록을 Location 헤더에 담아줌
  - ex) GET menu 하면 서버입장에선 `menu.jpg`, `menu.pdf`등
- `301` Moved Permanently
  - 요청한 URL이 옮겨졌을 때 사용한다. 응답은 현재 리소스가 위치하는 URL을 Location 헤더에 포함해야함
  - "영구이사" 느낌
- `302` Found
  - 301의 상태코드랑 같지만, 여기선 서버 공사중으로, "임시로" 변경된 페이지를 가르키는 목적으로 Location 헤더에 담아응답 
- `303` See Other
  - 클라이언트에게 리소스를 다른 URL에서 가져와야한다고 말해주는 것
  - Location 헤더에 새 URL응답 메시지가 포함
- `304` Not Modified
  - GET 같은 요청을 보냈을 때 리소스 수정사항이 없다면 수정되지 않았다는 사실을 응답으로 주고, 본문을 가지지 않음
- `305` Use proxy
  - 리소스가 반드시 프록시를 통해 접근되어야 함을 나타내기 위해 사용
  - Proxy 위치는 응답에 Location 헤더에 포함함
- `307` Temporary Redirect
  - 302랑 비슷
  
<br>

**`400-499` 클라이언트 에러 상태코드**
- `400` Bad Request
  - 클라이언트가 잘못된 요청을 보냈다.
- `401` Unauthorized
  - 사용자 인증을 해라
- `402` Payment Required
  - 현재는 사용하지 않지만 나중에 쓰일 가능성이 있음
- `403` Forbidden
  - 요청이 서버에 이해 거부됨(거절의 이유를 숨기고 싶을 때)
- `404` Not found
  - 서버가 요청한 URL을 찾을 수 없을 때 사용
- `405` Method Not Allowed
  - 그 메서드 못쓴다고 쓸 수 있는 메서드를 사용자에게 알려줌
- `406` Not Acceptable
  - 주어진 URL에 대한 리소스 중 클라이언트가 받아들일 수 없는 경우(요청에 Accept: json 이런식으로 보냈는데, 응답할 수 있는게 xml 뿐인 경우)
- `407` Proxy Authentication Required
  - 리소스에 대한 인증을 요구하는 프락시 서버를 이용
- `408` Request Timeout
  - 클라이언트 요청을 완수하기에 많은 시간이 걸리는 경우 응답을 끊을 때
- `409` Conflict
  - 리소스에 대해 일으킬 수 있는 몇몇 충돌이 생길 염려가 생길 때
- `410` Gone
  - 서버가 한 때 리소스를 갖고 있었지만 제거되었을 때
- `411` Length required
  - 서버가 요청 메시지에 Content-Length 헤더가 있을 것을 요구할 때
- `412` Precondition Failed
  - 클라이언트가 조건부 요청을 걸었지만 하나가 실패하였을 때(Expect 헤더를 포함했을 때)
- `413` Request Entity Too Large
  - 서버가 처리할 수 있는 범위를 넘어갔을 때
- `414` Request URL Too Long
  - 서버가 이해하거나 지원하지 않는 유형의 엔터티를 보냈을 때
- `415` Unsupported Media Type
  - 서버가 이해하거 지원하지 못하는 유형의 엔터티를 클라이언트가 보냈을 때
- `416` Requested Range Not Satisfiable
  - 요청에서 특정 메시지 리소스의 범위가 잘못됐을때
- `417` Expectation Failed
  - 요청에 포함된 Expect 요청 헤더에 서버가 만족시킬 수 없는 기대가 담겨있는 경우

**`500-599` 서버 에러 상태코드**
- `500` Internal Server Arror
  - 서버가 요청을 처리할 수 없게 만드는 에러를 만났을 때
- `501` Not Implemented
  - 클라이언트가 서버의 능력을 넘은 요청을 했을 때
- `502` Bad Gateway
  - 게이트웨이를 거쳐 서버에서 응답읇 받으려는데 거기서 특정 이유로 이상한 응답을 받았을 때
- `503` Service Unavailable
  - 현재 서버가 요청을 처리해줄 수는 없지만 나중에는 가능함을 의미
- `504` Gateway Timeout
  - 상태코드 408과 비슷하지만 다른 서버에게 요청을 보내고 응답을 기다리다 타임아웃이 발생한 게이트웨이나 프락시에서 온 응답이다.
- `505` Method Not Allowed
  - 서버가 지원할 수 없거나 지원하지 않으려고 하는 버전으로 된 요청을 받았을 때
  
### 버전번호
- HTTP/x.y 형식으로 요청과 응답에 모두 기술되어, 자신이 따르는 프로토콜의 버전을 상대방에게 말해주기 위한 수단으로 됨
- 명시하지 않으면 상태코드나 헤더 형태등등이 프로토콜마다 다르기 때문에 대화가 잘 안됨

## 📍 헤더
- `본문(body)`을 어떻게 처리해야 하는지 알려주는 설명서
### 일반헤더
- 일반 헤더는 누가 보내든 상관없이 이 메시지 자체에 대한 공통 정보들을 적는 헤더다.
  - Connection, Date, MEMI-Version...
- 일반 캐시헤더: HTTP/1.0은 HTTP 애플리케이션에게 매번 원 서버로 객체를 가져오는 대신, 로컬 복사본으로 캐시할 수 있도록 해주는 최초의 헤더를 도입함
  - Cache-Control, Pragma..
### 요청헤더
- 요청 메시지를 위한 헤더로 대한 부가정보를 제공
  - Client-IP, From, Host, User-Agent...
- Accept 관련 헤더
  - “나는 누구고, 이런 걸 원하고, 이 정도는 처리할 수 있다"를 서버에 알려줌
  - Accept, Accept-Charset..
- 조건부 요청 헤더
  - 클라이언트는 요청에 제약을 넣어서 서버에게 요청을 할 수 있음
  - Expect, If-Match, Range...
- 요청 보안 헤더
  - 클라이언트가 요청할 때 리소스에 접근하기 위해 본인을 인저하게 해서 트랜잭션을 안전하게 함
  - Authorization, Cookie, Cookie2...
- 프락시 요청 헤더
  - 프락시가 많아지며 그들의 기능을 돕기 위한 헤더
  - Max-Forwards, Proxy-Authorization, Proxy-Connection... 
### 응답헤더
- 클라이언트에게 정보를 제공하기 위한 응답에 대해 부가정보를 제공(누가 보내는지, 내 능력은 어떻게 되는지 등등..
  - Age, Public, Retry-After, Server..
- 협상 헤더
  - 여러가지로 표현이 가능한 상황에서 협상을 할 수 있도록 지원
  - Accept-Ranges, Vary...
- 응답 보안 헤더
  - 이 페이지를 이렇게 쓰면 안 된다라고 브라우저에게 명시
  - Proxy-Authenticate, Set-Cookies, WWW-Authenticate..
### 엔티티헤더
- 본문 크기와 콘텐츠, 혹은 리소스 그 자체를 서술
- 엔티티 내용물, 개체의 타입, 주어진 리소스에 대해 요청할 수 있는 유효한 메서드등을 제공
- 메시지의 수신자에게 자신이 다루고 있는 것이 뭔지 알려줌
- Allow, Location..
- 콘텐츠헤더
  - 엔티티의 콘텐츠에 대한 구체적인 정보를 제공
  - Content-Base, Content-Encoding..
- 엔터티 캐싱 헤더
  - 언제 캐시가 되어야하는지 지시자를 제공
  - 캐시된 사본이 유효한지, 언제 유효하게 되지 않았는지에 대한 정보 제공
  - ETag, Expires, Last-Modified..
### 확장헤더
- 명세에 정의되지 않은 새로운 헤더

## 📍 HTTP 지연
- HTTP는 TCP 바로 위에 있는 계층이기 때문에 TCP에 성능의 영향을 많이받음
- 트랜잭션을 처리하는 시간보다 많은 시간을 차지하는 것
  1. 클라이언트 URL에서 IP주소와 포트 번호를 알아내야함, DNS에서 이걸 변환하는데 시간
  2. TCP커넥션 요청으로 서버가 응답하기를 회신하는 시간(만약 수백개의 HTTP가 발생한다면?)
  3. 요청메시지를 TCP파이프라인에서 받아 읽고 처리되는데 소요되는 시간
  4. 응답을 보내는데 소요되는 시간

 <br>
 
### HANDSHAKE 지연 (연결)
1. 클라이언트가 TCP 커넥션 생성하기 위해 `TCP 플래그(SYN)`를 서버에 보낸다.
2. 서버가 받아들이면 `SYN`과 함께('니 요청 잘 받았다를 증명'하기 위해) `ACK` 플래그를 보낸다.
3. 확인 응답과 함께 서버에 HTTP 요청을 보냄
   - 근데 HTTP요청의 크기가 작은 경우라면 50%이상을 트랜잭션을 구성하는데 쓰는 것이다.

<br>

### 확인응답 지연(데이터 수신)
- 각 TCP 세그먼트는 순번과 데이터 무결성 체크섬을 가짐
- 세그먼트 수신자는 세그먼트를 온전히 받으면 확인응답 패킷을 송신자에게 반환함
- 3HandShake이후 받은 HTTP요청에 대한 응답을 전송할때 ACK를 `편승`시켜서 따로 보내지 않고 응답과 함께 보냄
  - ACK을 바로 보내지않고 같은 방향으로 가는 패킷(=편승할 패킷)이 없는 경우가 많아서 지연되는 경우가 많음

<br>

### TCP 느린 시작(Slow start) (전송량)
- TCP가 한 번에 전송할 수 있는 패킷의 수를 제한해서 급작스러운 부화와 혼잡을 제어한다.
- 네트워크 대역폭·혼잡 상태를 모르기 때문에 처음부터 많이 보내면 패킷 손실이 되면 재전송하는 일이 생김, 그래서 조금 보내며 잘 가는지 보고 늘리는 방식이다.
  - ACK를 기다리지 않고, 미리 정해진 윈도우(cwnd) 범위 안에서 데이터를 보내고, ACK이 오면 그 ACK를 기준으로 윈도우를 키운다.”

<br>

### 네이글 알고리즘과 TCP_NODELAY (패킷 크기)
- 작은 크기의 데이터를 포함한 많은 수의 패킷을 전송하면 네트워크의 성능이 많이 떨어진다.
- 그래서 네이글 알고리즘으로 패킷을 전송하기 전에 많은 양의 TCP데이터를 한개의 덩어리로 합친다.
- 크기가 작은 HTTP 메시지는 패킷을 채우지 못하기 때문에 지연이 생길 가능성이 있다.
- ACK을 편승시켜 보내는 확인응답지연과 같이 쓰면 그 ACK을 기다리는 시간이 길어져서 더 느려짐


<br>

### TIME_WAIT 누적과 포트 고갈 
- TCP는 패킷이 늦게 도착할 수 있는 네트워크로 예전에 보낸 패킷이 연결이 이미 끝난 뒤에 다시 도착할 수 있어서 새로운 연결로 착각할 수 있음
- 그걸 연결종료 후에 같은 4-tuple을 메모리에 임시에 저장해둬서 일정 시간 재사용 금지하도록 함
- 근데 이게 계속 쌓이거나 이거에 묶인 포트는 임시로 사용이 불가하다는 등의 문제가 있음 
- 4way handshake

## 📍 HTTP 커넥션 관리
### Connection 헤더
**예시**
```
Connection: X-Secret
X-Secret: abc123
```
→ “X-Secret 헤더는 이 연결에서만 의미 있으니 다음 중간 전달자한테 넘기지 마”<br>

1. HTTP는 end-to-end처럼 보이지만 실제로는 hop-by-hop으로 전달된다.
2. Connection 헤더는 **“바로 다음 홉에게만 하는 말”**이다.
3. 프록시는 Connection 헤더를 읽고 버린 뒤, 자기 정책대로 다시 쓴다.
4. 그래서 프록시는 앞·뒤 TCP 커넥션을 서로 다르게 관리할 수 있다.

## 📍 병렬 커넥션
- 여러개의 TCP 커넥션을 통한 동시 HTTP 요청
  - HTML은 객체로 이뤄져있는데 이걸 하나하나 내려받는건 너무 느리기 때문에 클라이언트가 병렬로 하나씩 내려받는 방법이 있음
- 클라이언트의 네트워크 대역폭이 좁을 때는 서로 대역폭을 쪼개 먹어서 전체 전송이 더 느려진다.
  - 100명의 사용자가 100개의 커넥션을 맺고 있으면 서버는 10,000개의 커넥션을 갖고있는 것임
- 각 트랜잭션마다 새로운 커넥션을 맺고 끊어서 시간, 대역폭 소요
- 각 새로운 커넥션은 TCP 느린시작 때문에 성능이 떨어짐
- 실제로 연결할 수 있는 병렬 커넥션 수에는 제한이 있음

<br><br>

## 📍 지속 커넥션
- 요청이 처리가 완료된 이후에도 TCP 커넥션을 유지해서 앞으로 있을 요청에도 계속 연결된 상태로 있는 TCP 커넥션
  - 클라이언트나 서버가 커넥션을 끊기 전까진 계속 연결됨
- 해당 서버에 맺어진 커넥션을 사용하면서 커넥션을 맺는 횟수와, 준비시간을 줄일 수 있음
- keep-alive랑은 http 프로토콜 버전의 차이

## 📍 지속커넥션 + 병렬커넥션
### HTTP/1.0의 한계
- HTTP/1.0 기본 동작은 요청 1개에 TCP 연결 1개해서, 응답 후 즉시 연결 종료
  - 매 요청마다 TCP 연결 생성, 3-way handshake 반복 => 지연 ↑, 서버 부하 ↑
- HTTP/1.0 keep-alive (비표준 확장) 해결 시도로 `Connection: keep-alive`을 써서 “이번 TCP 연결을 여러 요청에 재사용하자”고 하니 연결 비용이 감소하고, 성능이 향상됨
  - 하지만 표준이 아니라서 서버마다 구현 다르고, 지원 여부가 제각각
  - 프록시는 요청을 그대로 전달해서 keep-alive 헤더를 이해 못해서 연결 닫아버렸지만 클라이언트는 연결 살아있다고 착각해서 통신 오류 발생
  - 여기서 hop-by-hop 문제가 본격적으로 등장함
- HTTP 요청 경로는 `클라이언트 → 프록시 → 서버` TCP 연결은 hop 단위라서 `클라이언트↔프록시`, `프록시↔서버`는 완전히 별개 연결이다.
  - `keep-alive`는 `end-to-end`처럼 보이지만 실제로는 `hop-by-hop` 동작
  - 그래서 등장한 개념이 `hop-by-hop` 헤더로 지속 커넥션은 반드시 홉별로 제어되어야 한다. (= 현재 헤더는 현재 연결에서만 의미가 있으니 다른 홉으로 전달하면 안된다.)
- Connection 헤더의 진짜 역할 Connection 헤더는 지속 커넥션을 위해 도입된 장치다.
  - `Connection: keep-alive`: keep-alive 정보는 이 hop에서만 사용 다음 홉으로 전달하지마라.
- 프록시의 책임 
  - 프록시는 지속 커넥션을 쓸 경우 반드시 `hop-by-hop 헤더 제거`, 연결 단위로 상태 관리, 자신이 이해하지 못하는 `keep-alive`요청은 연결 종료해야함
  - 못지키면 데이터 유실, 연결 꼬임, 버그 발생

### HTTP/1.1의 등장 
- HTTP/1.x keep-alive는 hop-by-hop이라서 각 홉이 Connection 헤더를 해석·제거·재작성해야 하는 구조라서 번거로움
- HTTP/1.1 기본 정책 지속 커넥션이 기본으로, keep-alive 명시 필요 없고, 명시적으로 끊을 때만 `Connection: close` 사용
- 요청/응답 순서 보장, 파이프라이닝 가능, 프록시는 hop-by-hop 규칙을 반드시 준수, Connection 헤더는 계속 hop-by-hop 용도로 유지

## 📍 파이프라인 커넥션
- 공유 TCP를 통한 병렬 HTTP 요청

### 파이프라인 커넥션이란?
- 하나의 지속 커넥션에서 이전 요청의 응답을 기다리지 않고 여러 HTTP 요청을 연속으로 보내는 방식

### 생긴 이유
- 지속 커넥션은 요청–응답을 하나씩 기다려야 해서 느리고, 네트워크가 놀게 되니 “기다리지 말고 요청을 미리 보내자"는 의미로 파이프라인이 등장

### 장점
- 연결은 하나만 사용
- 네트워크 대기 시간 감소
- 응답을 더 빨리 받기 시작함

### 단점
- 한번에 보내면 응답 순서가 반드시 유지돼야 되는데 그게 어려움
- 앞 요청의 응답이 느리면 뒤 요청의 응답이 전부 대기함 (HOL Blocking)
- 프록시/서버가 완전히 지원해야 안전
- TCP자체에서는 패킷의 순서도 맞춰줘야함(TCP HOL Blocking) -> 해결위해 HTTP/3 QUIC(UDP에서 만들어짐) - 장비단에서 처리하던걸 application 단으로 올려서 로직화?함 (AWS ALB도 그런것처럼 로드벨런서를 로직단으로 올림)

## 📍 커넥션 끊기
### 생긴 이유
- HTTP/1.1은 기본이 `keep-alive`인데 서버/프록시/클라이언트 중 누군가 더 이상 연결을 유지하고 싶지 않을 때 그냥 TCP를 끊어버리면 상대는 왜 끊겼는지 모르고, 요청 재전송하는 문제가 생겨서  “이 응답 끝나면 끊을 거다”를 명시적으로 알리는 방법
- 다 보냈다고 알리고(FIN), 상대가 다 받았다고 확인한 뒤 정상 종료하는 우아한 끊기와 같은 것들이 있다.


## 📍 CORS (Cross-Origin Resource Sharing)
### 개념
- 서로 다른 출처(Origin) 간의 자원을 공유하는 메커니즘. 웹에는 기본적으로 SOP(Same-Origin Policy, 동일 출처 정책)가 존재하여 브라우저가 허락한 곳에서만 데이터를 가져가도록 강제한다.

### 오리진(Origin)의 구성
- Protocol(http/https) + Host(naver.com) + Port(8080, 443 등)

### 동작 방식
1. 브라우저가 요청 헤더에 Origin을 담아 보낸다.
2. 성공 시 서버는 Access-Control-Allow-Origin을 응답 헤더에 담아 보내며, 이용 가능한 도메인, 허용 메서드(GET, POST), 쿠키 사용 여부 등을 지정해 줄 수 있다.
3. 실패하면 CORS 에러가 발생한다.
