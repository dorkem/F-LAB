## TCP 소켓 프로그래밍
- TCP는 연결 지향 프로토콜이라서, 통신 전에 연결을 먼저 맺고(3-way handshake) 데이터가 순서대로, 빠짐없이 전달되도록 보장함.
- `소켓(Socket)`은 프로그램이 네트워크로 데이터를 보내고 받기 위한 `통신 창구(인터페이스)`

### 서버
1. 소켓 생성
2. 포트에 바인딩
3. 연결 대기(listen)
4. 클라이언트 연결 수락(accept)
5. 데이터 송수신
6. 연결 종료

### 클라이언트
1. 소켓 생성
2. 서버에 연결(connect)
3. 데이터 송수신
4. 연결 종료

## HTTP 지연
- HTTP는 TCP 바로 위에 있는 계층이기 때문에 TCP에 성능의 영향을 많이받음
- 트랜잭션을 처리하는 시간보다 많은 시간을 차지하는 것
  1. 클라이언트 URL에서 IP주소와 포트 번호를 알아내야함, DNS에서 이걸 변환하는데 시간
  2. TCP커넥션 요청으로 서버가 응답하기를 회신하는 시간(만약 수백개의 HTTP가 발생한다면?)
  3. 요청메시지를 TCP파이프라인에서 받아 읽고 처리되는데 소요되는 시간
  4. 응답을 보내는데 소요되는 시간

 <br>
 
### HANDSHAKE 지연 (연결)
1. 클라이언트가 TCP 커넥션 생성하기 위해 `TCP 플래그(SYN)`를 서버에 보낸다.
2. 서버가 받아들이면 `SYN`과 함께('니 요청 잘 받았다를 증명'하기 위해) `ACK` 플래그를 보낸다.
3. 확인 응답과 함께 서버에 HTTP 요청을 보냄
   - 근데 HTTP요청의 크기가 작은 경우라면 50%이상을 트랜잭션을 구성하는데 쓰는 것이다.

<br>

### 확인응답 지연(데이터 수신)
- 각 TCP 세그먼트는 순번과 데이터 무결성 체크섬을 가짐
- 세그먼트 수신자는 세그먼트를 온전히 받으면 확인응답 패킷을 송신자에게 반환함
- 3HandShake이후 받은 HTTP요청에 대한 응답을 전송할때 ACK를 `편승`시켜서 따로 보내지 않고 응답과 함께 보냄
  - ACK을 바로 보내지않고 같은 방향으로 가는 패킷(=편승할 패킷)이 없는 경우가 많아서 지연되는 경우가 많음

<br>

### TCP 느린 시작(Slow start) (전송량)
- TCP가 한 번에 전송할 수 있는 패킷의 수를 제한해서 급작스러운 부화와 혼잡을 제어한다.
- 네트워크 대역폭·혼잡 상태를 모르기 때문에 처음부터 많이 보내면 패킷 손실이 되면 재전송하는 일이 생김, 그래서 조금 보내며 잘 가는지 보고 늘리는 방식이다.
  - ACK를 기다리지 않고, 미리 정해진 윈도우(cwnd) 범위 안에서 데이터를 보내고, ACK이 오면 그 ACK를 기준으로 윈도우를 키운다.”

<br>

### 네이글 알고리즘과 TCP_NODELAY (패킷 크기)
- 작은 크기의 데이터를 포함한 많은 수의 패킷을 전송하면 네트워크의 성능이 많이 떨어진다.
- 그래서 네이글 알고리즘으로 패킷을 전송하기 전에 많은 양의 TCP데이터를 한개의 덩어리로 합친다.
- 크기가 작은 HTTP 메시지는 패킷을 채우지 못하기 때문에 지연이 생길 가능성이 있다.
- ACK을 편승시켜 보내는 확인응답지연과 같이 쓰면 그 ACK을 기다리는 시간이 길어져서 더 느려짐


<br>

### TIME_WAIT 누적과 포트 고갈 
- TCP는 패킷이 늦게 도착할 수 있는 네트워크로 예전에 보낸 패킷이 연결이 이미 끝난 뒤에 다시 도착할 수 있어서 새로운 연결로 착각할 수 있음
- 그걸 연결종료 후에 같은 4-tuple을 메모리에 임시에 저장해둬서 일정 시간 재사용 금지하도록 함
- 근데 이게 계속 쌓이거나 이거에 묶인 포트는 임시로 사용이 불가하다는 등의 문제가 있음

## HTTP 커넥션 관리
### Connection 헤더
**예시**
```
Connection: X-Secret
X-Secret: abc123
```
→ “X-Secret 헤더는 이 연결에서만 의미 있으니 다음 중간 전달자한테 넘기지 마”<br>

1. HTTP는 end-to-end처럼 보이지만 실제로는 hop-by-hop으로 전달된다.
2. Connection 헤더는 **“바로 다음 홉에게만 하는 말”**이다.
3. 프록시는 Connection 헤더를 읽고 버린 뒤, 자기 정책대로 다시 쓴다.
4. 그래서 프록시는 앞·뒤 TCP 커넥션을 서로 다르게 관리할 수 있다.

<br><br>

## 병렬 커넥션
- 여러개의 TCP 커넥션을 통한 동시 HTTP 요청
  - HTML은 객체로 이뤄져있는데 이걸 하나하나 내려받는건 너무 느리기 때문에 클라이언트가 병렬로 하나씩 내려받는 방법이 있음
- 클라이언트의 네트워크 대역폭이 좁을 때는 서로 대역폭을 쪼개 먹어서 전체 전송이 더 느려진다.
  - 100명의 사용자가 100개의 커넥션을 맺고 있으면 서버는 10,000개의 커넥션을 갖고있는 것임
- 각 트랜잭션마다 새로운 커넥션을 맺고 끊어서 시간, 대역폭 소요
- 각 새로운 커넥션은 TCP 느린시작 때문에 성능이 떨어짐
- 실제로 연결할 수 있는 병렬 커넥션 수에는 제한이 있음

<br><br>

## 지속 커넥션
- 요청이 처리가 완료된 이후에도 TCP 커넥션을 유지해서 앞으로 있을 요청에도 계속 연결된 상태로 있는 TCP 커넥션
  - 클라이언트나 서버가 커넥션을 끊기 전까진 계속 연결됨
- 해당 서버에 맺어진 커넥션을 사용하면서 커넥션을 맺는 횟수와, 준비시간을 줄일 수 있음

<br><br>

## 지속커넥션 + 병렬커넥션
### HTTP/1.0의 한계
- HTTP/1.0 기본 동작은 요청 1개에 TCP 연결 1개해서, 응답 후 즉시 연결 종료
  - 매 요청마다 TCP 연결 생성, 3-way handshake 반복 => 지연 ↑, 서버 부하 ↑
- HTTP/1.0 keep-alive (비표준 확장) 해결 시도로 `Connection: keep-alive`을 써서 “이번 TCP 연결을 여러 요청에 재사용하자”고 하니 연결 비용이 감소하고, 성능이 향상됨
  - 하지만 표준이 아니라서 서버마다 구현 다르고, 지원 여부가 제각각
  - 프록시는 요청을 그대로 전달해서 keep-alive 헤더를 이해 못해서 연결 닫아버렸지만 클라이언트는 연결 살아있다고 착각해서 통신 오류 발생
  - 여기서 hop-by-hop 문제가 본격적으로 등장함
- HTTP 요청 경로는 `클라이언트 → 프록시 → 서버` TCP 연결은 hop 단위라서 `클라이언트↔프록시`, `프록시↔서버`는 완전히 별개 연결이다.
  - `keep-alive`는 `end-to-end`처럼 보이지만 실제로는 `hop-by-hop` 동작
  - 그래서 등장한 개념이 `hop-by-hop` 헤더로 지속 커넥션은 반드시 홉별로 제어되어야 한다. (= 현재 헤더는 현재 연결에서만 의미가 있으니 다른 홉으로 전달하면 안된다.)
- Connection 헤더의 진짜 역할 Connection 헤더는 지속 커넥션을 위해 도입된 장치다.
  - `Connection: keep-alive`: keep-alive 정보는 이 hop에서만 사용 다음 홉으로 전달하지마라.
- 프록시의 책임 
  - 프록시는 지속 커넥션을 쓸 경우 반드시 `hop-by-hop 헤더 제거`, 연결 단위로 상태 관리, 자신이 이해하지 못하는 `keep-alive`요청은 연결 종료해야함
  - 못지키면 데이터 유실, 연결 꼬임, 버그 발생

### HTTP/1.1의 등장 
- HTTP/1.x keep-alive는 hop-by-hop이라서 각 홉이 Connection 헤더를 해석·제거·재작성해야 하는 구조라서 번거로움
- HTTP/1.1 기본 정책 지속 커넥션이 기본으로, keep-alive 명시 필요 없고, 명시적으로 끊을 때만 `Connection: close` 사용
- 요청/응답 순서 보장, 파이프라이닝 가능, 프록시는 hop-by-hop 규칙을 반드시 준수, Connection 헤더는 계속 hop-by-hop 용도로 유지

## 파이프라인 커넥션
- 공유 TCP를 통한 병렬 HTTP 요청

### 파이프라인 커넥션이란?
- 하나의 지속 커넥션에서 이전 요청의 응답을 기다리지 않고 여러 HTTP 요청을 연속으로 보내는 방식

### 생긴 이유
- 지속 커넥션은 요청–응답을 하나씩 기다려야 해서 느리고, 네트워크가 놀게 되니 “기다리지 말고 요청을 미리 보내자"는 의미로 파이프라인이 등장

### 장점
- 연결은 하나만 사용
- 네트워크 대기 시간 감소
- 응답을 더 빨리 받기 시작함

### 단점
- 응답 순서가 반드시 유지돼야 되기 때문에 앞 요청의 응답이 느리면 뒤 요청의 응답이 전부 대기함 (HOL Blocking)
  - 프록시/서버가 완전히 지원해야 안전

## 커넥션 끊기
### 생긴 이유
- HTTP/1.1은 기본이 `keep-alive`인데 서버/프록시/클라이언트 중 누군가 더 이상 연결을 유지하고 싶지 않을 때 그냥 TCP를 끊어버리면 상대는 왜 끊겼는지 모르고, 요청 재전송하는 문제가 생겨서  “이 응답 끝나면 끊을 거다”를 명시적으로 알리는 방법
- 다 보냈다고 알리고(FIN), 상대가 다 받았다고 확인한 뒤 정상 종료하는 우아한 끊기와 같은 것들이 있다.
