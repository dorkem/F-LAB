## CORS(Cross-Origin Resource Sharing)
- 서로 다른 출처간의 자원을 공유하는 메커니즘
- 브라우저가 허락한 곳에서만 데이터를 가져가라고 강제하는 규칙으로, 웹에는 SOP(Same-Origin Policy)가 존재한다.

### 오리진의 구성
- `Protocol`(https/http), `Host`(naver.com), `Port`(8080, 443..)
- 이걸 브라우저가 요청 헤더에 담아 보내고, 성공하면 `Access-Control-Allow-Origin`를 보내주고, 이용가능한 도메인과, 메서드(`GET`, `POST`), 쿠키 사용 여부 등을 지정해줄 수 있음
- 실패하면 CORS

## Redis
### 레디스란
- Remote Dictionary Server로 `Key-Value` 형태로 저장하고 관리하는 전용 서버를 말한다.(해시테이블 자료구조를 사용한다)
  - 파이썬의 `Dictionary` = 자바의 `Map`
  - 사용하는 자료구조는, `Strings`(키-값), `Lists`(Queue로 활용), `Sets`(중복없는 집합), `Sorted Sets`(실시간 랭킹등), `Hashes`(필드-값)

### 특징
- 인메모리 기반으로 RAM(메모리)에 저장한다.
  - 그래서 특정 시점마다 메모리를 스냅샷을 찍어놓음
  - 모든 쓰기 명령을 메모장에 적듯이 파일 끝에 추가된다.(레디스의 로컬디스크에 저장됨)
- 싱글스레드로 동작한다.
  - I/O 멀티플렉싱(이벤트 루프)방식을 사용하는데 램에 접근하니까 결과가 빠르게 나온다.
    - 이벤트 루프: 요청이 생기기 전까지 대기하기 때문에 일반 루프랑은 다름
    - 동작과정은 이벤트 큐에 이벤트가 쌓이고, 이벤트 루프가 새로운 루프가 있는지 큐에서 확인하고, 핸들러가 이벤트를 처리한다.
- `DB`로 쓰기엔 관계를 맺는다던가, 비싸다는 문제가 있음

## 분산락
### 문제정의
- 단일 서버라면 자바의 `synchronized`등으로 해결이 되지만, 서버가 2대인 상황에서는 같은 상품을 동시에 서버 A, B에서 주문이 동시에 들어올 때와 같은 상황에서 문제가 발생한다.
  - 공통의 관리자가 필요하다.
 

### 방법 및 종류
- 임계 영역에 진입하기 직전에 Redis에 특정 키를 생성해달라고 요청해서 열쇠를 얻은 서버의 로직을 수행함, 작업이 끝나면 레디스에서 해당 키를 삭제해서 다음 순서 실행
- `Lettuce`(스핀락)은 `SETNX`로 레디스에 키가 있는지 무한으로 물어봐서 부하가 크다.
- `Redisson`(Pub/Sub)은 락이 풀리면 레디스가 알림을 주는 구조로 부하가 적다.
  - 대기(Subscribe): 서버 한대가 락을 잡고 있으면, 서버 B는 레디스한테 락 풀리면 알려달라고 기다림
  - 알림(Publish): 서버 A가 일을 다 마치면 신호를 보냄
 

 ### 문제점
 - `DeadLock`: 서버가 락을 잡고 일하다가 갑자기 죽으면 열쇠가 반납되지 못하는 경우가 발생
   - 타임아웃을 설정해서 서버가 죽어도 시간이 지나면 자동해제됨(레디스에 키를 걸 때 TTL옵션을 같이 보냄)
 - 트랜잭셔널 내부에 락을 걸면, 락이 풀리기 전에 누군가 조회하는 경우 옛날 데이터를 볼 수도 있어서, `트랜잭셔널 바깥에서 걸어줘야함`
 - 락을 api 전체 등 넓은 범위로 잡으면 서비스가 마비될 수 있어서, 좁은 범위로 잡아줘야함

### 거는 법
1. 레디스에 `lock:user:{userId}` 라는 키가 있는지 확인하고 TTL설정 후, 있다면 구독
2. 커밋
3. finally등에 레디스내에 `userId` 키 삭제

## 메모리 캐시와 분산 캐시의 차이점
### 메모리 캐시(Local Cache)
- 주소 목록 같은 잘 변하지 않는 정보들을 저장함
- 추가적인 인프라 비용이 들지 않음
- 네트워크를 타지 않고 내 메모리에서 가져오니까 더 빠름

### 분산 캐시(Distributed Cache)
- 로그인 세션 정보(사용자가 서버1에서 로그인 했어도 서버 2가 그걸 알아야 할 때)
- 실시간 재고, 랭킹등 모든 서버가 동일한 숫자를 보고 수정해야할 때 등 데이터 불일치 문제가 해결됨

### 확장성
- `메모리 캐시`는 애플리케이션 서버의 `Heap` 영역이 너무 커지면 GC가 동작할 때 `Stop-the-world`라는게 길게 동작하여 서비스가 마비될 수 있다.
- `분산 캐시`는 캐시 전용 서버라서 메모리용량을 늘릴 수 있고, 여러대의 서버를 묶어서 관리가 가능하다.
  - Redis는 C언어로 만들어져서 GC가 없고, 데이터 저장에만 모든 메모리를 사용하기 때문에 확장성이 좋다.(컴퓨터 램 늘리는 것보다 레디스 서버를 추가하는게 더 쉽다)

### 로그 방식과 분산 캐시 방식
- 로그 방식
  - 서버1이 업데이트 로그를 쓰면, 서버 2,3,4가 그걸 보고 업데이트함
    - 서버 100대면 메시지 100개를 써서 네트워크 부하가 발생한다.
  - 서버 2는 받았는데 3은 네트워크 오류로 못받으면 데이터가 서버마다 달라지는 문제가 발생한다.
- 분산 캐시 방법
  - 서버 1개가 레디스에 데이터 수정했다고 기록하면 나머지 서버는 그걸 보고 고치기만 하면 됨
 
### 용도
- 세션 클러스터링으로 로그인 유지
- 얘도 메모리기반이라 속도는 빠름

### 매 api 요청마다 외부저장소 조회가 병목일지, 감내 가능할지에 대한 판단기준
- 솔직히 정합성을 위해 네트워크 속도를 희생할지, 빠른 처리를 위해 약간의 정합성을 포기해야할지 트레이드 오프 관계인 것 같음
- 평균 시간
  - 메모리 캐시: 10 ~ 100 나노초
  - 분산 캐시: 0.1 ~ 2 밀리초
  - 데이터베이스: 10 ~ 100 밀리초
- 네트워크 대역폭과 커넥션 갯수
  - 서버에서 레디스로 연결하는 통로가 부족하면 요청이 밀림
  - 한번에 많은 데이터를 가져오면 네트워크 대역폭을 다 써버려서 전체가 느려진다.
- 부하 테스트 확인
  - 초당 요청 수를 늘려서 레디스의 CPU 점유율과 네트워크 사용량을 보고 로컬 캐시 도입을 고려해야한다.

## 로그인 방식
### 세션 (Session) 방식

- 동작 원리: 사용자가 로그인하면 서버는 사용자의 상태 정보를 서버의 메모리나 DB에 저장합니다. 그리고 사용자를 확인 할 수 있는 고유한 'Session ID'를 생성하여 Set-Cookie를 통해 클라이언트에게 전달합니다. 그러면 브라우저는 API를 호출할 때마다 발급받은 Session Cookie를 요청에 담아 보내며, 서버는 매 요청마다 자기가 보관하고 있는 Session ID와 대조하여 사용자를 확인합니다.
- 한계: 서비스 규모가 커져서 여러 대의 서버를 운영(Scale-out)할 경우, A 서버에서 로그인한 사용자가 B 서버로 이전할 때 세션 공유가 되지 않아 로그아웃되는 문제가 발생할 수 있습니다. 이를 해결하기 위해서 Redis같은 외부 저장소를 사용할 수 있지만, 대규모 트래픽 환경에서는 매 API 요청마다 외부 저장소를 조회해야 하므로 병목이 발생합니다.


### JWT (JSON Web Token) 방식

- 토큰 발급: 로그인 시 DB를 대조하여 계정 정보가 일치하면, 서버는 엑세스 토큰(Access Token)과 리프레시 토큰(Refresh Token)을 생성합니다.
  - `엑세스 토큰` (JWT): 헤더(Header), 페이로드(Payload), 시그니처(Signature)의 세 부분으로 구성됩니다. 페이로드 에는 유저 ID와 만료 시간 등의 정보가 Base64로 인코딩되어 담깁니다. 시그니처는 인코딩된 헤더와 페이로드, 그리고 서버만 알고있는 비밀키(Secret Key)를 조합한 뒤 해시 함수를 돌려 생성하는 서명 과정을 거칩니다.
  - `리프레시 토큰`: 엑세스 토큰 만료 시 재발급을 위한 토큰으로, 유저 ID를 Key로 하고 복잡한 난수를 Value로 DB에 저장해 둡니다.
- 인증 과정 (Stateless): 클라이언트는 API 요청 시 HTTP 헤더에 Authorization: Bearer <엑세스토큰> 형태로 토큰을 담아 보냅니다. 서버의 필터는 DB 조회 없이 서버가 가진 비밀키만으로 시그니처 유효성을 검증합니다. 서명 검증에 통과하면 페이로드를 디코딩하여 유저 정보를 확인하고 비즈니스 로직을 실행합니다.
- 토큰 갱신 (Refresh): 서버는 페이로드의 만료 시간을 확인해 기한이 지났다면 인증 만료 응답(401)을 보냅니다. 이때 클라이언트가 리프레시 토큰을 담아 /refresh 엔드포인트로 POST 요청을 보내면, 서버는 DB에 저장된 리프레시 토큰과 대조한 뒤 유효할 경우 새로운 엑세스 토큰을 발급하여 내려줍니다.


### 결론
 결과적으로 매 API 요청마다 DB를 반드시 거쳐야 하는 세션 방식과 다르게, JWT는 토큰 자체에 정보랑 서명을 가지고 있어서 DB접근 없이 서버 필터 단에서 검증이 가능하므로 서버 확장이나 트래픽이 많이 발생하는 경우에 유리하고, 이 점을 봤을 때 소셜 로그인 구현시에 JWT가 용이하다고 생각됩니다.
