# 👨‍🏫 강의
## 1) SRP, OCP등의 객체지향과 구현 방법들

### 응집도(Cohesion)
- 응집도는 하나의 객체(또는 클래스) 안에 있는 데이터와 메서드가 동일한 책임을 위해 얼마나 밀접하게 관련되어 있는지를 의미한다.

- 예를 들어, 어떤 클래스에 name과 age라는 필드가 있고,
`getName()`은 `name`만 사용하고 `getAge()`는 `age`만 사용한다면
각 필드는 자신과 관련된 메서드에서 100% 사용되므로 응집도가 높다.


- 반대로, 하나의 메서드가 클래스 내부 필드 중 일부만 사용하거나
필드가 여러 책임에 걸쳐 부분적으로(예: 50%) 사용된다면
그 클래스는 여러 책임이 섞여 있고 응집도가 낮다고 볼 수 있다.

즉, SRP를 지킨 클래스일수록 응집도가 자연스럽게 높아진다.

<br>

### SRP (Single Responsibility Principle)

- SRP는 한 클래스가 하나의 역할과 책임만 가져야 한다는 원칙이다.

- 클래스가 여러 책임을 가지면:
필드와 메서드 간의 연관성이 약해지고
수정 시 “왜 이 코드가 여기에 있지?”라는 의문이 생기며
변경 영향 범위가 커진다.

- 따라서 SRP는 클래스를 잘게 나누기 위한 규칙이 아니라 `응집도를 높여` 변경과 이해를 쉽게 만들기 위한 기준이다.

<br>

### 결합도(Coupling)

- 결합도는 한 객체가 다른 객체의 구체적인 구현에 얼마나 강하게 의존하고 있는지를 나타낸다. 예를 들어,

```java
class Team {
    Member member = new Member();
}
```


- 이처럼 클래스 내부에서 new로 객체를 직접 생성하면 `Team`은 `Member`라는 구체 클래스 없이는 아예 동작할 수 없게 된다.
- 이 상태가 결합도가 높은 구조이다.

<br>

반면,
```java
class Team {
    Member member;

    Team(Member member) {
        this.member = member;
    }
}
```

- 이처럼 외부에서 객체를 주입받으면
`Team`은 “`Member`가 어떤 구현인지” 몰라도 되고,
결합도가 낮아진다.

<br>

###  OCP (Open-Closed Principle)

- OCP는 “확장에는 열려 있고, 변경에는 닫혀 있어야 한다” 는 원칙이다.
- 이 말은 새로운 기능이 필요할 때 기존 코드를 수정하지 않고 새로운 구현을 추가하는 방식으로 확장해야 한다는 뜻이다.
- 이것이 가능하려면 인터페이스를 기준으로 의존해야 하고 결합도가 낮아야 하며 `DI와 IoC 구조`가 전제되어야 한다.

<br>

### IoC (Inversion of Control) — 토비의 스프링 관점

- `IoC(제어의 역전)` 는 객체 생성, 의존 관계 설정, 실행 흐름에 대한 제어권을 애플리케이션 코드가 아니라 외부에 위임하는 설계 원칙이다.
- 토비의 스프링에서는 이를 “객체가 자신이 사용할 객체를 직접 선택하거나 생성하지 않는다” 라고 설명한다.
- 초기의 IoC는 팩토리 객체를 두어 객체 생성 책임을 한 곳으로 모으는 방식으로 시작되었고 이 팩토리 객체가 바로 IoC의 가장 원형적인 형태이다.
- 즉, IoC는 개념(설계 원칙) 이고 “누가 객체를 만들고, 누가 관계를 관리하느냐”에 대한 이야기다.

<br>

### DI (Dependency Injection) — 스프링에 더 가까운 개념
- `DI(의존성 주입)` 는 IoC를 구현하는 대표적인 방법이며,
- 토비의 스프링에서는 IoC를 실현하는 가장 현실적이고 표준적인 방식으로 설명된다.
- 객체가 필요한 의존성을 직접 new로 생성하지 않고 외부(팩토리, 컨테이너)가 만들어서 생성자, 세터, 필드 등을 통해 주입받는다.

- `스프링`에서는 이 역할을 `IoC 컨테이너`(Bean Factory, ApplicationContext) 가 수행하며, 개발자는 객체 생성과 연결에 대한 코드를 작성하지 않고 객체의 역할과 로직에만 집중하게 된다.


<br>


### 2) AOP
```
🙋‍♂️ 나:
메서드마다 로그 출력이나 실행 시간 측정을 직접 넣기 시작하면 처음에는 단순해 보이지만,
이런 코드가 수십·수백 개로 늘어나는 순간 핵심 로직과 상관없는 코드들이 여기저기 섞이면서 전체 구조가 급격히 복잡해진다.
만약 이 작업을 500개의 메서드, 500개의 클래스에 적용해야 한다면
모든 메서드 앞뒤에 코드를 추가하거나 공통 메서드를 호출하는 방식으로는 유지보수가 사실상 불가능해진다.


이 문제를 해결하기 위해 등장한 개념이 AOP다.
AOP는 로깅, 시간 측정, 트랜잭션처럼 여러 곳에서 반복되는 공통 기능을 비즈니스 로직과 분리하고,
 메서드 실행 전·후에 자동으로 끼워 넣는 방식의 프로그래밍이다.
그래서 AOP를 흔히 ‘껴넣기 프로그래밍’이라고 부르며,
핵심 로직은 그대로 둔 채 부가 기능만 선택적으로 적용할 수 있게 해준다.


이 방식은 데코레이터 패턴과 개념적으로 맞닿아 있다.
데코레이터 패턴은 기존 객체의 기능을 변경하지 않고, 그 앞이나 뒤에 기능을 덧붙이는 패턴인데,
AOP는 이 패턴을 프레임워크 차원에서 자동으로 적용해주는 구조라고 볼 수 있다.


스프링에서는 AOP를 사용하기 위해 개발자가 프록시 객체를 직접 만들 필요가 없다.
@Service 같은 애노테이션으로 빈을 등록하면 스프링 컨테이너가 AOP 설정(@Aspect)을 확인한 뒤 “이 빈은 AOP 대상이다”라고 판단하고,
원본 객체 대신 프록시 객체를 생성해 컨테이너에 등록한다.
그래서 우리가 주입받아 사용하는 객체는 실제 구현체가 아니라, 그 앞에 세워진 프록시 객체다.


이 프록시는 일종의 대리인 역할을 한다. 클라이언트가 프록시를 호출하면,
프록시는 먼저 로깅이나 시간 측정 같은 부가기능을 수행한 뒤 실제 대상 객체에게 작업을 위임하고,
작업이 끝난 후에도 필요한 후처리를 수행한다.
덕분에 비즈니스 로직은 공통 기능의 존재를 전혀 몰라도 되고, 코드의 응집도는 유지된다.


프록시를 만드는 방식에는 두 가지가 있다.
JDK 동적 프록시는 인터페이스 기반으로 동작하기 때문에 반드시 인터페이스가 필요하며,
프록시는 해당 인터페이스를 구현한 대리 객체로 생성된다. 반면 CGLIB 프록시는 인터페이스가 없어도 동작하며,
대상 클래스를 상속해 바이트코드 레벨에서 프록시 클래스를 생성한다.
이 방식에서는 메서드를 오버라이드해 실행 전·후에 부가기능을 삽입한다.


다만 CGLIB 방식에는 제약이 있다. final이나 private 메서드는 오버라이드할 수 없기 때문에 AOP를 적용할 수 없고,
객체 내부에서 자기 자신의 메서드를 호출하는 경우(self-invocation)에는 프록시를 거치지 않기 때문에 트랜잭션이나 AOP가 적용되지 않는다.
즉, 스프링 AOP는 항상 프록시를 통해 외부에서 호출될 때만 동작하며, 이 특성을 이해해야 AOP나 트랜잭션이 적용되지 않는 이유를 정확히 설명할 수 있다.


결국 AOP는 공통 기능을 분리해 코드의 복잡도를 낮추고, 핵심 로직의 응집도를 유지하면서도 확장성과 유지보수를 가능하게 만드는 설계 기법이다.
```
