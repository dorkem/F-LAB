# 📜 자바

##  📍 ArrayList와 LinkedList의 차이점

### 1. 배열과 리스트의 기본 개념
- `배열(Array)`: 메모리에 순차적으로 할당되며 크기가 고정되어 있다.
- `리스트(List)`: 자바 컬렉션 인터페이스로, 배열의 한계를 극복해 가변적으로 데이터를 추가/제거할 수 있다.


<br>

### 2. ArrayList vs LinkedList 비교
- `ArrayList`: 내부적으로 연속된 배열을 사용해 조회가 빠르다. 하지만 중간 삽입·삭제 시 요소를 당기거나 미는 연산(`System.arraycopy()`)이 필요해 $O(n)$의 비용이 발생한다.
- `LinkedList`: 비연속적 노드 구조라 조회가 느리다. 양 끝단의 삽입·삭제는 링크만 변경해 $O(1)$로 매우 빠르지만, 중간 삽입·삭제는 해당 노드까지 탐색해야 하므로 똑같이 $O(n)$이 소요된다.

<br>

### 3. Queue/Deque의 최적 구현체 (ArrayDeque)
- `LinkedList`는 양 끝단 연산이 빠르다는 장점 때문에 Queue 구현체로 자주 쓰이지만, 삽입할 때마다 새로운 노드 객체를 생성하는 메모리 오버헤드(데이터를 넣기 위해 새로운 힙으로 공간을 할당하는 것)가 있다.
- `ArrayDeque`는 내부적으로 원형 배열(Circular Array)을 사용하여 양 끝단 삽입·삭제를 모두 $O(1)$로 처리한다.
  - 노드 생성 오버헤드가 없고 연속된 메모리를 사용해 CPU 캐시 지역성(Cache Locality)이 뛰어나므로, 데이터 확장이 극단적이지 않다면 LinkedList보다 성능상 더 유리하다.
  - 캐시 지역성: 배열 기반이라면 `LinkedList`와는 다르게 메모리상에 연속으로 붙어있기 때문에 1번의 데이터를 읽어올 때 2, 3번 데이터도 같이 캐시에 딸려옴

### 4. GC(가비지 컬렉션) 관점
- 데이터 삭제 시 즉각적인 GC가 발생하지 않고 최적의 시점에 일괄 처리되므로, GC 비용만으로 두 자료구조를 비교하는 것은 무의미하다. (단, 객체 재할당이 극단적으로 잦은 환경에서는 고려해야 함)

## 📍 힙과 스택의 차이
### 스택
- 메서드의 실행 순서를 기억하고, 그 안에서만 잠깐 쓰고 버릴 임시 데이터들을 빠르고 안전하게 `관리`하기 위해 존재한다.
- 쓰레드(Thread)가 생성될 때마다 쓰레드별로 독립적인 스택 영역이 하나씩 할당된다. (쓰레드 간 `공유 불가`)
- 메서드가 호출될 때마다 '스택 프레임'이라는 블록이 `LIFO`(후입선출) 구조로 쌓인다(Push).
  - 이 안에는 지역 변수, 매개변수, 힙 영역에 있는 객체의 `참조 주소값`이 저장된다.
- 메서드 실행이 끝나면 해당 프레임은 스택에서 즉시 자동으로 `제거`(Pop)된다. 메모리 할당/해제 속도가 매우 빠르다.

<br>

### 힙
- 크기가 크거나, 여러 메서드/쓰레드에서 공유해야 하는 데이터(객체)를 `저장`하기 위해 존재한다.
- JVM이 구동될 때 단 하나의 힙 영역이 메모리에 크게 할당되며, JVM 안의 모든 쓰레드가 이 공간을 `공유`한다.
- 코드에서 new 키워드를 사용해 클래스의 인스턴스(객체)나 배열을 생성할 때 힙 영역에 실제 데이터가 `할당`된다.
  - 스택에 있는 변수들이 이 힙 메모리의 주소를 가리키는(참조하는) 방식으로 연결된다.
- 어떤 스택에서도 더 이상 참조하지 않는 '고아 객체(Unreachable Object)'가 되면, `가비지 컬렉터`(GC)가 주기적으로 메모리를 청소할 때 해제된다.


<br><br>


## 📍 JVM (Java Virtual Machine)
### 1) 등장 배경과 WORA (Write Once, Run Anywhere)
- 과거에는 C/C++처럼 운영체제(Windows, Linux 등) 환경에 맞춰 코드를 각각 다르게 컴파일해야 했다.
- 자바는 컴파일러가 소스코드(.java)를 운영체제가 아닌 JVM이 이해할 수 있는 `바이트코드(.class)`로 변환하고
- 이를 각 OS에 설치된 JVM이 번역하여 실행하므로 "한 번 작성하면 어디서든 실행"할 수 있다.

<br>

### 2) JVM의 4가지 핵심 컴포넌트
1. 클래스 로더 (Class Loader)
    - 자바 프로그램이 실행될 때, 컴파일된 `바이트코드`(.class) 파일들을 찾아 엮어서 JVM의 `메모리 영역`(Runtime Data Area)으로 `적재`(Load)하는 역할을 한다.
    - 필요한 클래스만 그때그때 메모리에 올리는 동적 로딩을 지원한다.
2. 런타임 데이터 영역 (Runtime Data Area)
    - JVM이 프로그램을 수행하기 위해 OS로부터 할당받은 `메모리 공간`이다.
    - 앞서 다룬 `스택(Stack)`과 `힙(Heap)` 영역뿐만 아니라,
    - 클래스(설계도) 정보와 static 변수가 저장되는 `메서드(Method)` 영역,
    - 스레드가 현재 실행 중인 주소를 가리키는 `PC 레지스터` 등으로 세분화되어 있다.
3. 실행 엔진 (Execution Engine)
    - 메모리에 적재된 바이트코드를 컴퓨터(기계)가 이해할 수 있는 네이티브 코드로 변환하여 실제 명령을 실행한다.
    - `인터프리터 (Interpreter)`: 코드를 한 줄씩 읽고 번역해서 실행한다. (초기 실행은 빠르나 전체 속도가 느림)
    - `JIT 컴파일러 (Just-In-Time Compiler)`: 인터프리터의 느린 속도를 보완하기 위해, 자주 반복되는 코드를 발견하면 이를 한 번에 기계어로 컴파일해 두고 캐싱하여 실행 속도를 비약적으로 끌어올린다.
4. 가비지 컬렉터 (Garbage Collector, GC)
    - 백그라운드에서 동작하며, 힙(Heap) 영역에서 더 이상 어떤 스택이나 변수에서도 참조하지 않는 '고아 객체(Unreachable Object)'를 탐색하고 주기적으로 메모리에서 제거하여 공간을 최적화한다.

<br>

### JIT 컴파일러
- 코드를 한 줄씩 읽으면서 기계어로 즉시 번역(해석)하고 바로 실행하는 인터프리터 방식과, 실행 전에 코드 전체를 기계어로 미리 번역하는 컴파일러 방식을 섞어서 사용한다.
- 인터프리터 방식으로 실행하다가, 어떤 메서드가 반복적으로 호출하는지 프로파일링하고, 특정 코드가 많이 실행되는 부분은 기계어로 번역해서 캐시로 저장해서 그걸 실행함.

<br><br>

## 📍 프로세스와 스레드의 차이

### 1) 본질적인 차이
- `프로세스(Process)`
  - OS로부터 할당받은 독립된 메모리 공간(Code, Data, Heap, Stack)을 갖는 프로그램의 실행 단위.
  - 완전히 분리되어 있어 서로 데이터를 주고받으려면 별도의 통신(IPC)이 필요하며, 무겁고 생성 비용이 크다.
  - 실행중인 프로그램이다. (예: 자바 프로그램 실행 = JVM 프로세스 1개 생성)
- `스레드(Thread)`
  - 프로세스 내부에서 실제 코드를 실행하는 흐름의 단위.
  - 자신이 속한 프로세스의 자원(Code, Data, Heap)을 다른 스레드들과 `공유`하되, 스택(Stack) 영역만 `개별`적으로 갖는다.
  - 자원을 공유하므로 프로세스보다 가볍고 생성 비용이 적다.
- 스레드 실행 메서드 비교
  - `start()`: OS에 새로운 스레드 생성을 요청하고, 그 새 스레드 위에서 `run()`을 실행한다.
  - `run()`: 새로운 스레드 생성 없이, 호출한 현재 스레드(ex: main)에서 일반 메서드처럼 실행된다.

<br>

### `IPC`
  - 서로다른 프로세스들이 데이터를 주고받기 위해 사용하는 통로이다.
  - OS가 보안과 안정성을 위해 각 프로세스마다 메모리를 할당해서 침범이 불가능하지만, 개발할 때는 필요해서 만듦
  - 공유 메모리를 통해 두 프로세스의 공용 메모리 공간을 만들어 준다던지, OS가 두 프로세스 사이에서 편지를 대신 전달해주는 메시지 패싱방법등이 있다.
  - 각기 다른 프로세스는 언어나 메모리 주소 체계나 위치등이 다 다른데, 이걸 직접적으로 소통할 수 없어서 `인터페이스`로 이런 규칙으로 대화하자고 정해둠

<br>

### 2) 동시성(Concurrency) vs 병렬성(Parallelism)
- `동시성` (단일 코어 관점)
  - 여러 작업을 아주 빠르게 번갈아 가며 실행(Context Switching, RR 스케줄링)하여, 사람 눈에 동시에 처리되는 것처럼 보이게 만드는 논리적인 기법이다.
- `병렬성` (멀티 코어 관점)
  - 여러 개의 CPU 코어가 물리적으로 서로 다른 작업을 정확히 같은 시간에 동시에 실행하는 것이다.
  - 코어 자체가 나뉘어 일하므로 작업 간 Context Switching이 발생하지 않는다.

<br>

 ### 3) 공유 자원과 동시성 제어
 - `크리티컬 섹션`(Critical Section)
   - `스레드`들은 프로세스의 `힙(Heap)` 영역을 `공유`하기 때문에, 여러 스레드가 동시에 접근하여 데이터를 변경하려 할 때 데이터 불일치(Race Condition)가 발생할 수 있다.
   - 이렇게 동시 접근 시 문제가 생기는 `코드`나 `자원 영역`을 뜻한다.
 - 자바의 동시성 문제 해결
   - `synchronized` 키워드 (또는 Lock)
     - 한 스레드가 자원을 선점하면 락(Lock)을 걸어 다른 스레드가 접근하지 못하게 막고 순차적으로 처리한다.
   - `Atomic` 클래스
     - 하드웨어 수준의 원자성을 보장하여 동시성 문제를 해결한다. (예: AtomicInteger)
   - `Concurrent` 컬렉션
     - 멀티스레드 환경에 맞춰 스레드 안전성(Thread-safe)을 내장한 자료구조이다. (예: ConcurrentHashMap)
   - `volatile` 키워드
     - CPU 캐시가 아닌 메인 메모리(RAM)에서 직접 값을 읽고 쓰도록 강제하여, 모든 스레드가 항상 가장 최신의 값을 보도록 가시성을 보장한다.
   - `뮤텍스와 세마포어`
     - 운영체제에서 자원에 접근할 수 있는 열쇠를 관리하는 방식
     - `뮤텍스`: Mutual Exclusion(상호 배제)의 줄임말로 1명이 열쇠를 들고 들어가서 문을 잠그고, 나올때 열쇠를 반납한다.
     - `세마포어`: 유량제어(Read)용
   - `CAS`(=낙관적 락, 아토믹)
     - 데이터를 읽기 전부터 누가 건드릴 수도 있으니 일단 문부터 잠그는 일반적인 락(비관적 락)과 다르게, 건드리지 않을 것이라 생각하고 문을 잠그지않고 계산한 후에, 마지막 데이터를 저장하기 전에 변경되지 않았는지 확인하는 방법( 만약에 누가 건드렸으면 수정취소됨 )
   - `ConcurrentHashMap`
     - 일반적인 Hashtable은 싱크로나이즈를 붙여서 뮤텍스락을 사용하니 누가 데이터를 하나만 고쳐도, 전체 데이터를 다 잠궈버리지만, 얘는 구역별로 나눠서 만지는 부분만 잠근다. 해시맵은 암것도 안써서 멀티스레드에서 사용하지 못함 

<br><br>

## 📍 Primitive Type과 Wrapper Class의 차이
- 자바에서 기본형(int 등)은 객체가 아니어서 null을 가질 수 없고 스택에 저장되지만,
- 래퍼 클래스(Integer 등)는 객체로 힙에 저장되며, 둘 사이의 연산은 오토 박싱·언박싱을 통해 가능하다.

<br><br>

## 📍 SET
- Set(특히 HashSet)은 원소의 “동등성”을 판단할 때 hashCode()로 먼저 같은 후보를 찾고,그다음 equals()로 진짜 같은지 확정한다.
- 그래서 Set에 넣는 객체는 equals()와 hashCode()를 “함께” 일관되게 재정의해야 한다.

<br><br>
